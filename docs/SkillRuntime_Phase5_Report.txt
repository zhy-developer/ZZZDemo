2. 实际修复与影响

F1 缺帧后无法可靠恢复（客户端运行缺陷）
证据 MissingFrame-Repro/：真实 UDP 丢包后收到后续帧但不推进，预算超时，未完成对局。
根因：历史 lackFrame 填充/发送代码被注释，AddLackFrameData 又以该空列表为接纳条件；高帧游标还能被乱序旧包降低。
BattleData.AddNewFrameData：保留首次接纳输入，忽略重复覆盖，最高收到帧单调增加。
BattleData.AddLackFrameData：在已校验对局作用域后接纳尚未消费且不超过最高收到帧的缺失数据，重复不覆盖。
BattleManager.LogicUpdate：Pilot 遇到缺口每0.25秒请求现有补帧协议，最多32帧区间；已有连续帧每次调用最多处理8帧。
每帧仍完整 ConsumeFrame -> RunOpSucces；缺下一帧不编造输入，终局立即停止。Legacy每次仍最多1帧。
不改变33ms技能步长、协议格式、几何/伤害/结果优先级。墙钟只决定网络重试，不决定战斗结果。
验证：Unity Lifecycle 新增9项（原19+9=28），真实故障代理连续测试与输入/状态逐帧对齐。

F2 关闭 UDP 对端影响正常对局（服务端运行缺陷）
证据 Soak-01/：运行约550秒、3场完成后，协议测试退出的 UDP 端点引发 Windows ConnectionReset；

UdpManager 初始化 Windows 共享 UDP socket 时设置 SIO_UDP_CONNRESET(0x9800000C)=false；
ConnectionReset 异常兜底继续接收，不休眠、不把单端 ICMP 当业务裁决。
BattleService.GetRequestFrames 的正常补帧日志从 LogError 改为 [FrameReplay] Log，消除正常补帧的错误堆栈洪水。
未清除待确认对局、未新增断线判负/超时选边。

Phase5FrameRecorder：每Match最多10000帧，单次工具最多24个Match；每日志256MiB运行器上限，代理队列4096。
行键 match/round/frame/stage；规范输入按battleID排序，移动方向规范化，保留原动作ID/type/value1/value2。
缺少槽位保留为缺少，空操作不会被当作缺帧。配置/规则/seed参与匹配。
hash是SHA256(UTF8)，字段Ordinal顺序，以UTF16字符长度前缀+字段名和值构建无歧义字符串。
先逐帧比较规范输入，再比较全部具名状态，再比较hash；必须从F1连续，无重复，无缺少Match/尾帧。
首次分歧保留差异字段、双方行和前4行上下文。相同hash也不能掩盖不同具名字段。
14条独立工具断言含实际JSONL读写、输入优先、相同旧hash/不同运动字段、空文件、缺帧、重复帧、缺Match。

本轮实际故障主要是停在缺帧/接收阻塞/代理退出，没有观察到“相同已消费输入计算出不同权威状态”的实例。
MissingFrame-Repro的早期记录器未及时flush，失败后的帧文件不完整；不能据此声称已取得完整失败输入回放。
后续记录器前128帧逐帧flush，此后每128帧flush；最终完成的对局在Dispose完整落盘，再进行严格连续帧校验。
首个字段差异功能由独立工具的真实JSONL差异用例验证；实际通过运行报告的是未发现分歧，而非伪造差异帧。
初始条件来自固定BattleScene、显式开发profile、同一match/session及行内randSeed；故障种子固定0x51f15e。
Unity/网络线程调度会影响实际故障命中哪些输入，精确战斗输入以JSONL为准；不宣称墙钟代理时序跨机器逐包一致。

5. 网络条件、连续运行和性能口径

真实UDP代理同时作用上下行：基础20ms+0..60ms抖动，序号每37包丢1、每29包复制1且额外延后90ms形成乱序。
每场Ready起4.0～4.6秒丢下行帧；每场第一次终局上报、第一次Confirmed丢弃；新Ready后1秒注入旧Match帧。
TCP保持其正常有序传输，没有伪造“TCP逐包乱序”；业务重复另用WireChecks标注。
ClientA目标60fps、B目标30fps，每场分别人为阻塞渲染线程250/450ms一次，网络线程继续接收。
输入驱动只操作真实出站输入和登录/匹配；不写HP、不注入入站逻辑帧、不跳过真实结算。
连续场景先2100帧重复Normal链，再由一方真实追击至终局，交替施放方；客户端离场节奏至少覆盖1800秒。
每场完成不止看hash：另断言HP/生死、完整终局帧、双方确认一次、两端退役、重新入场身份/初态、终局冻结。
代理实际包计数、种子、逐场输入和日志留档。首个报告/确认丢失后靠原业务重试恢复。

性能：Stopwatch测Advance开始至已提交阶段；单独统计含表现的Advance总时间（排除诊断序列化时间）。
渲染批次统计同一Time.frameCount累计的权威耗时及逻辑帧数量；输入消费始终按连续帧。
backlog取最高已收帧减已消费帧，是待补齐/处理的帧号跨度，包含缺口，不冒称已到齐的队列元素数。
每场mean/P95/P99/max和样本量保留，不对多场P95取平均后冒称全局P95。
GC.Alloc的UnitType=TimeNanoseconds，其Count用于分配事件数，Value不能当字节。
实际Mono的GC.GetAllocatedBytesForCurrentThread不工作（8192字节探针仍为0）：stats标false和-1，不报告“零分配”。
原生GC Allocated In Frame计数器单位Bytes，提供整个Unity渲染帧的字节量，含渲染/诊断/加载，不能当纯战斗关键路径字节。
因此交付关键路径分配次数+全渲染帧字节量；关键路径精确分配字节仍受此环境API限制。
外部ProcessSamples.csv采样有效Windows进程内存/句柄/线程；Mono内部private/handles为0，不用于趋势判断。
GC.CollectionCount在此Mono各代相同，不宣称三种独立代际GC；统计gc0及局限。
所有性能均Development+Profiler观察器；诊断关闭仍有计时/分配测量开销。非Release基准，未做超范围数学优化。
尚无项目正式性能阈值，性能结论必须标待定；33ms仅逻辑步长，不等于批准了33ms CPU峰值预算。
